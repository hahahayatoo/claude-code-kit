# アーキテクチャ設計・実装計画

要件に基づいて詳細な実装計画を作成します。

## 実装モデルを前提とした計画作成

この計画書を実装するのは **Sonnet モデル**（tdd-agent）です。
Sonnet は指示に忠実に従いますが、曖昧な記述から意図を汲み取る能力は限定的です。
そのため、計画書は以下の原則に従って**具体的かつ明示的**に記述してください。

### 記述の原則
- **関数シグネチャを明示**: 名前、引数、戻り値の型を具体的に記述する
- **ファイルパスを正確に記述**: `src/utils/validator.ts` のようにフルパスで指定する
- **テストケースの期待値を明示**: 具体的な入力と期待される出力を記述する
- **判断を委ねない**: 「適切に実装」「必要に応じて」のような曖昧な表現を避ける
- **依存関係を明示**: import すべきモジュール、使用すべき既存の関数・クラスを明記する
- **エッジケースの扱いを決定**: エラー時の挙動、境界値の処理を計画段階で確定させる

### 避けるべき記述例と改善例

| 避けるべき記述 | 改善例 |
|---------------|--------|
| 「バリデーション関数を作成」 | 「`validate(input: string): Result<T, Error>` を作成。空文字の場合は `InvalidInputError` を返す」 |
| 「テストを書く」 | 「入力 `"abc"` → 戻り値 `{ valid: true }`、入力 `""` → `InvalidInputError` をテスト」 |
| 「適切なエラーハンドリング」 | 「ネットワークエラー時は `ConnectionError` を throw し、リトライは呼び出し側に委ねる」 |
| 「既存のユーティリティを活用」 | 「`src/utils/format.ts` の `formatDate()` を使用して日付を ISO8601 形式に変換」 |

## 最重要原則: 推測の禁止

**要件に記載されていない事項を推測・仮定で補完してはいけません。**

- requirements.md に書かれていない要件を勝手に追加しない
- 技術選定で迷う場合は、推測せず AskUserQuestion で確認する
- アーキテクチャの選択肢が複数ある場合は、選択肢を提示してユーザーに選ばせる
- 「一般的には〜」「ベストプラクティスでは〜」を理由に勝手に決定しない

## Web調査
技術選定やアーキテクチャ設計にあたり、公式ドキュメントやインターネット検索で事実確認すること。
調査で得た情報は計画書に反映し、参照元URLを記載する。

## 日付取得
日付・日時を出力する際は `date` コマンドを使用する（ISO8601: `date -Iseconds`、YYYYMMDD: `date +%Y%m%d`）。

## ワークフローフォルダ

1つの要望（イシュー）に対する成果物は `docs/workflows/{YYYYMMDD}-{feature_name}/` に集約されています。
このフォルダを作成するのは `/hear` であり、`/architect` は **既存のフォルダに計画書を追加する** 立場です。

最初に `docs/context/current-state.json` の `workflow_dir` を読み、以降このドキュメントで `{workflow_dir}` と
書かれている箇所はそのパスを指すものとして扱ってください。入力（`requirements.md` / `handoff.md` /
`review-results.md`）も出力（`plan.md`）もすべてこのフォルダ配下にあります。

**`workflow_dir` が存在しない場合のフォールバック**（旧形式の state を引き継いだケース）:
`feature_name` と `date +%Y%m%d` から `docs/workflows/{YYYYMMDD}-{feature_name}/` を組み立てて作成し、
`current-state.json` に `workflow_dir` を設定してから続行する。既存の入力ファイルが `docs/context/` 直下に
ある場合は、そのパスを読んだうえで出力のみ新フォルダに書く。

## 進捗管理（TodoWrite）

以下の主要ステップを TodoWrite で管理し、進捗をユーザーに可視化してください。

- pending としての初期登録は、タスク内容が確定した時点で行う（動作モード判定の後に、モードに対応する一覧を登録する）
- 各ステップ開始時に `in_progress` に更新する（同時に in_progress は1つだけ）
- 各ステップ完了時に即座に `completed` に更新する（完了をまとめて更新しない）

主要ステップ（新規計画モード、タスク 0〜5 に対応）:
- handoff.md 引き継ぎと技術スタック確定
- 要件分析
- アーキテクチャ検討
- タスクサイズ判定と分割
- テスト計画
- 計画書作成

主要ステップ（修正計画モード、タスク 1〜4 に対応）:
- 指摘事項の分析
- 根本原因の特定
- 修正の影響範囲の調査
- 修正計画の作成

## 動作モード

docs/context/current-state.json を確認し、動作モードを判定してください。

### 新規計画モード
- current_phase が "hear" の場合
- → 要件に基づいて新規の実装計画を作成する
- `{workflow_dir}/requirements.md`（= `current-state.json` の `requirements_file`）から要件を読み込む

### 修正計画モード
- current_phase が "review" かつ review_result が "NEEDS_WORK" または "REJECT" の場合
- かつ、has_critical_or_major が true の場合
- → レビュー指摘に基づいて修正計画を作成する
- `{workflow_dir}/review-results.md`（= `current-state.json` の `review_results_file`）から指摘事項を読み込む
- docs/context/current-state.json の plan_file から元の計画書を参照する

### レビュー未完了モード
- current_phase が "review" かつ review_result が "PARTIAL" の場合
- → 修正計画は作成しない。以下のメッセージを出力して終了:
  「レビューが部分的にしか完了していません。`/code-review` をリトライして全観点の結果を揃えてから /architect を再実行してください。」

### エラー
- 上記いずれにも該当しない場合は、まず /hear を案内してください。

## 新規計画モードのタスク

> **注意**: このセクション（タスク 0〜5 および計画書フォーマット）は新規計画モード専用です。修正計画モードでは実行しないでください。

### 0. handoff.md の引き継ぎと技術スタック確定

`{workflow_dir}/handoff.md`（= `current-state.json` の `handoff_file`）が存在するか確認する。

#### handoff.md がある場合（通常ケース：/hear から遷移）
- `handoff.md` を技術スタック・ディレクトリ構成の **起点** として扱う
- 記載されている情報はそのまま採用し、以下を確定する：
  - language, test_framework, test_command, file_extension, src_dir, test_dir, migration_tool（DB利用時のみ）
- 不明点・確認が必要な点（test_command の正確な引数、複数候補がある場合の選択、handoff.md と現在のコードに乖離がある可能性など）があれば、必要な範囲でコードを読むか AskUserQuestion で確認する

#### handoff.md がない場合（/hear をスキップして直接 /architect された場合）
既存コードベース（ビルド設定ファイル、ディレクトリ構造）を調査し、以下を確定する。
判断できない場合は AskUserQuestion で確認する。

確定する項目: language, test_framework, test_command, file_extension, src_dir, test_dir, migration_tool（DB利用時のみ）

### 1. 要件分析
`{workflow_dir}/requirements.md` を読み込み、要件を理解する。

### 2. アーキテクチャ検討
既存コードとの整合性を確認し、変更が必要なコンポーネントを特定する。

`handoff.md` がある場合は「ヒアリング中に得た補足コンテキスト」セクション（要件外情報、調査中に発見した懸念、architect への申し送り）を必ず参照し、設計判断に反映する。

複数のアプローチが考えられる場合は、選択肢とトレードオフを提示し AskUserQuestion でユーザーに選択してもらう。

### 3. タスクサイズ判定と分割
以下に該当する場合は大規模と判定し、イテレーションに分割する：
- 変更ファイル数6以上、新規作成4以上、テストケース11以上のいずれか
- 複数の独立した機能を含む

分割の原則: 機能単位で独立テスト可能、依存される側を先に、技術リスクが高いものを先に。
1イテレーション = テストケース3-7件、変更ファイル1-3の規模。

### 3.5. 複数案並列生成と選択

Task 3 でタスクサイズと大まかな方向性が固まった後、**3 focus 並列** で実装アーキテクチャを生成し、ユーザーに選択させる。**単一のアシスタントメッセージ内で 3 つの Task ツール呼び出しを並列送信** すること。

**修正計画モードでは本 Task 3.5 は実行しない**（修正計画は既存のシリアル実行を維持する）。

#### 起動する 3 エージェント

`code-architect-agent` を以下の focus で並列起動:

- `focus=minimal`: 最小変更・最大再利用のアプローチ
- `focus=clean`: 抽象化と保守性を優先（リファクタリング許容）
- `focus=pragmatic`: minimal と clean の中間、バランス型

#### 各エージェントに渡すプロンプト内容

- `focus`: 上記のいずれか
- `requirements`: `{workflow_dir}/requirements.md` の要点（またはパス指定で Read させる）
- `handoff context`: `handoff.md` の技術スタック・既存ファイル情報の要点
- `task breakdown`: Task 2 のアーキ検討結果と Task 3 のタスク分割方針

#### 結果の受け取り

各 architect は return value で以下形式を返す:
```
focus: <name>
## Approach Summary
...
## Pros
- ...
## Cons
- ...
## Files to create/modify
- ...
## Key design decisions
- ...
## Notes
- ...
```

正規表現 `^focus:\s*(minimal|clean|pragmatic)$` で各応答の focus を識別する。

#### 3 案の比較と推奨案の明示

main Claude は以下を実施:

1. 3 応答の Approach / Pros / Cons を **比較表** で並べる
2. **推奨案を 1 つ明示** する
3. 推奨の判定基準（優先順位）:
   1. **要件との整合性**（requirements.md との一致度）
   2. **実装コスト**（変更ファイル数・工数）
   3. **保守性**（長期的な変更容易性）
4. 推奨案の理由を短く（2-3 文）述べる

#### 選択 UX

AskUserQuestion で 3 案から選択させる:
- options: 3 案（Minimal / Clean / Pragmatic、推奨案を先頭に "(推奨)" 表記）
- 「Other」は AskUserQuestion 標準機能に任せる（明示的な追加オプションは設けない）

選択された案を Task 4-5 のベースとする。

#### 特殊ケース

- **3 案が本質的に同一**（要件が単純で選択肢が実質ない）→ AskUserQuestion をスキップし、そのまま Task 4 へ。「3 案とも本質的に同一のため直接進行」とユーザーに伝達
- **部分失敗（3 並列中 1-2 失敗）** → 成功した案だけで比較・選択させる。「M/3 案のみ提示（失敗: <focus 名>）」とユーザーに伝達
- **3 案とも失敗** → ユーザーにリトライを促す。計画書は書き出さない

### 4. テスト計画
各イテレーションに対応するテストケースを計画する。

### 5. 計画書作成
以下の「計画書フォーマット」に従い、`{workflow_dir}/plan.md` に保存する。
（日付と機能名はワークフローフォルダ名が持つため、ファイル名では繰り返さない）

## 修正計画モードのタスク

> **注意**: このセクション（タスク 1〜5 および修正計画フォーマット）は修正計画モード専用です。新規計画モードでは実行しないでください。

### 1. 指摘事項の分析
`{workflow_dir}/review-results.md` を読み込み、Critical / Major の指摘をすべて把握する。

### 2. 根本原因の特定
複数の指摘が同一の根本原因に起因していないかを分析する。
対症療法ではなく、根本的な修正方針を検討する。

### 3. 修正の影響範囲の調査
review-results.md に記載されたファイル:行の情報を手がかりに、指摘に関連する既存コードを読み込む。
修正が他のコンポーネントに与える影響を確認する。
設計判断が必要な場合（例: セキュリティ対策の方式選定）は AskUserQuestion でユーザーに確認する。

### 4. 修正計画の作成
元の計画書ファイル（plan_file）に「修正計画」セクションを追記する。

### 5. 状態更新
docs/context/current-state.json を更新:
- current_phase: "fix-planned"
- updated_at: [ISO8601形式]

## 修正計画フォーマット

元の計画書ファイルの末尾に以下を記述する。
既に「修正計画（レビュー指摘対応）」セクションが存在する場合は、**前回の修正計画を削除してから新しい修正計画を記述する**（上書き）。

```markdown
---

## 修正計画（レビュー指摘対応）

### 根本原因分析
[複数の指摘に共通する根本原因があればここに記述]

### 修正ステップ

#### 修正 1: [指摘の要約]
- 重要度: [Critical / Major]
- 対象ファイル: [フルパス]
- 修正内容: [具体的な修正手順。「実装モデルを前提とした計画作成」の記述原則に従い、関数シグネチャ・具体的な処理内容・import パスを明示すること]
- 修正後の関数シグネチャ: [変更がある場合。名前・引数・戻り値の型を明示]
- 影響範囲: [この修正で影響を受ける他のファイル/関数]

#### 修正 2: ...

### テスト追加
- [ ] [修正に伴って追加すべきテストケース: 入力 → 期待出力]

### Minor 指摘（計画不要・直接修正可）
- [Minor 指摘はここにリストし、tdd-agent が直接修正する]
```

## 計画書フォーマット

```markdown
# 実装計画: [機能名]

## 概要
[1-2文で機能を説明]

## 要件サマリー
[requirements.md から引用]

## 技術スタック
- 言語: [language]
- テストフレームワーク: [test_framework]
- テストコマンド: [test_command]
- ファイル拡張子: [file_extension]

## ディレクトリ構成
- ソースコード: [src_dir]/
- テストコード: [test_dir]/

## タスクサイズ
- 判定: [小規模 / 中規模 / 大規模]
- イテレーション数: [N]
- 理由: [判定理由]

## アーキテクチャ
[変更が必要なコンポーネント、新規作成するファイル]

## 確認事項（必要時のみ）

**実装中に判断が必要になる可能性のある論点** がある場合、`## 確認事項` セクションを設けて列挙する。

設計段階では決め切れず、実装を進めるうえで初めて判断材料が揃うような事項を記載する。設計段階で決められる事項は、アーキテクチャ・タスク計画にあらかじめ反映すること（このセクションには含めない）。

論点が **存在しない場合はセクション自体を省略してよい**（形式的に「なし」と書く必要はない）。

tdd-agent はこのセクションがあれば読み込み、**該当する論点に実装中に達した時点で必ず AskUserQuestion でユーザーに確認** する（推測で実装を進めない）。

例:
- **N+1 クエリが発生した場合の最適化方針**: 実装してみるまで N+1 が出るか不明。出た場合に eager loading で解決するか、別クエリで取得するかをユーザーに確認する
- **外部 API のレスポンス形式が想定と異なった場合の扱い**: ドキュメントから推測した形式と実物がズレた場合に、どうフォールバックするかを確認する

各項目は「**論点 + どんな状況で判断が必要か + 想定される選択肢**（あれば）」の形式で記述する。「実装時に確認」のような曖昧な表現は避け、**何を / いつ確認するか** を具体的に書く。

---
```

## 状態更新

### 新規計画モードの場合
計画書作成後、以下を更新する：

1. **docs/context/current-state.json**: current_phase を "architect" に更新し、plan_file（= `{workflow_dir}/plan.md`）, total_iterations, current_iteration(=1), language, test_framework, test_command, file_extension, src_dir, test_dir, migration_tool, updated_at を設定。フォールバックで `workflow_dir` を作成した場合は `workflow_dir` も設定する
2. **CLAUDE.md**: 「プロジェクト設定」テーブルの `<!-- /architect で設定 -->` を確定値に置換

### 修正計画モードの場合
修正計画追記後、以下を更新する：

1. **docs/context/current-state.json**: current_phase を "fix-planned"、updated_at を設定
2. plan_file は変更しない（既存の計画書ファイルに追記するため）

## 次のステップ

### 新規計画モードの場合
計画が承認されたら、`/implement` でイテレーション1のTDD実装を開始してください。

#### イテレーション完了時のフロー

```
/implement → /test → /code-review → /commit
    ↓
（次のイテレーションがあれば）
    ↓
/plan-check → /implement へ
```

全イテレーション完了後、機能全体の統合テストを実施してください。

### 修正計画モードの場合
修正計画が作成されたら、`/implement` で修正計画に基づいた修正を実行してください。

```
/implement（修正計画実行モード） → /test → /code-review → /commit
```
